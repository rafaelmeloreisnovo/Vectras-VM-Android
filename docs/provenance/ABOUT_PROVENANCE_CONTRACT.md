# About Provenance Contract

Status: governance contract  
Date: 2026-09-04  
Scope: human-facing attribution/provenance disclosure for distributed Vectras-VM-Android / RAFAELIA builds.

## Purpose

The About surface is not a branding-only page. It is the human-readable projection of the repository's canonical authorship, license, transformation-lineage and build-identity records.

It MUST preserve upstream origin rather than replacing it with local branding.

## Canonical sections

### 1. Current project
Display current project identity, current repository and current maintainership.

Do not imply that maintainership equals authorship of inherited code.

### 2. Upstream / base
For each material upstream/base included in the distributed artifact, expose when known:

- project/component name;
- canonical source/repository;
- upstream version/ref/commit;
- license identifier/text reference;
- copyright/NOTICE reference;
- state: `UPSTREAM_EXACT` or `UPSTREAM_MODIFIED`;
- whether local changes exist.

### 3. Local modifications
Describe local changes as modifications, additions, replacements or original modules.

Allowed wording examples:

- `Based on <upstream>; modified by the RAFAELIA project.`
- `This component contains upstream code plus locally authored modifications.`
- `This module is ORIGINAL_VERIFIED within the current repository scope.`

Disallowed without evidence:

- `Entirely original` when inherited lineage exists.
- `Official <upstream>` without authorization.
- `Written by RAFAELIA` when only the modification is local.

### 4. Third-party software and assets
Expose required notices/licenses for distributed dependencies, binaries, firmware, fonts, images, rootfs, BIOS/OVMF, libraries and other assets.

Unknown rights or origin MUST render as a release-blocking gap, not a guessed license.

### 5. Build and source identity
Expose or make reachable:

- app version/versionCode;
- source commit/ref;
- build identifier;
- artifact digest where practical;
- SBOM/NOTICE reference when available.

Do not expose secrets, signing keys, private paths or private personal data.

### 6. Provenance/compliance state
Human-readable state MUST remain evidence-bounded.

Examples:

- `Provenance: PARTIAL — open upstream/license gaps remain.`
- `Security controls: mapped; certification not asserted.`
- `Runtime verification: TOKEN_VAZIO for this build.`

The About page MUST NOT state certification unless external attestation evidence exists for the exact scope/version.

## Data sources

The About representation SHOULD be generated from or validated against:

1. `LICENSES_REGISTER.md`
2. `THIRD_PARTY_NOTICES.md`
3. `resources/compliance/ASSET_PROVENANCE_REGISTER.csv` when present
4. transformation-lineage records governed by `docs/provenance/AGENTS.md`
5. build/source metadata generated by CI/build tooling
6. a machine-readable About manifest when introduced

Hard-coded identity/social/contributor data in Android activities/resources is secondary and MUST NOT override canonical provenance records.

## Reconciliation gate

Before release, compare:

`packaged_components <-> provenance_registry <-> licenses/notices <-> About disclosure <-> source/build identity`

Release fails when any material mismatch exists.

## Transformation disclosure rule

If upstream material has been changed, the About/credits layer MUST preserve both truths:

`upstream authorship/origin` **and** `local modification authorship`.

Transformation never converts inherited origin into local origin.

## Unknown-origin wording

When origin is unresolved but the component is under investigation, use wording equivalent to:

> Origin is pending verification and is treated as upstream/third-party for attribution purposes. No claim of local authorship is made.

If distribution rights are also unresolved, the component MUST be excluded from release or quarantined.

## Historical continuity

Do not delete an upstream credit merely because a later version replaces or rewrites the component. Historical receipts preserve lineage. The current About surface may describe only currently distributed components, but historical provenance remains append-only in repository records.

## Acceptance gate

An About implementation is acceptable only when:

- every displayed authorship claim is supported by provenance evidence;
- every material shipped upstream/third-party unit can be traced to a canonical record;
- local modifications are distinguishable from inherited content;
- required licenses/notices are reachable;
- build/source identity matches the artifact under review;
- unresolved material gaps are typed and do not masquerade as certainty.
